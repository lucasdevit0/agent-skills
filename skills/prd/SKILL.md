# Write a product requirements document

Start with a real situation. Who is trying to do what, how do they do it today, and where does that break down? Ask for a recent example if the idea is still an abstract feature request. State the outcome in terms someone could observe after release.

## Establish the baseline

Read the supplied brief, relevant product docs, existing implementation and related work. An open issue can describe intent while a released screen shows different behavior. Label each accordingly. Use an issue tracker when one is connected. A conversation and a local project are enough to draft a PRD.

Walk through the proposed experience as the people involved. Find where roles, existing records, unusual states or a second entry point change the answer. Ask about choices that would materially change the experience. Give a recommendation and explain its cost. Keep service and implementation choices for the technical plan unless they constrain the product.

## Draft for the person who picks it up

- Describe the problem, who experiences it, and the outcome that would count as success.
- Show one user journey from the first action through the visible result.
- Give each requirement an observable acceptance condition. Include exceptions where the user would reasonably expect different behavior.
- Name the boundaries, deferred ideas, unresolved questions and decisions already made. Indicate which questions block implementation.
- Link the relevant designs, existing issues and evidence. Suggest consolidation where two issues would deliver the same outcome.

A small change can fit in a single issue. For a larger project, keep the PRD readable on its own and leave a short list of decisions for breakdown. Return a draft by default. When asked to publish an agreed draft, update the specified destination and check the resulting document.
